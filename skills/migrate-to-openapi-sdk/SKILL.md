Migrate **$ARGUMENTS** (or ask which service/resource, if not given) onto the
OpenAPI-generated-client SDK pattern: backend routes decorated/typed for
code-first spec generation → a spec dumped with no server running → a typed
client generated by `@hey-api/openapi-ts` on an axios base → a thin
aggregator the frontend imports through, with a real JWT auth layer
(access + rotating refresh tokens) wired via axios interceptors.

**Templates live in `templates/` next to this file.** Copy them into the
target repo and fill in the `{{PLACEHOLDER}}` values — don't regenerate this
logic from scratch each time. The templates encode real bugs that were found
and fixed the hard way (see **Known gotchas** below); reinventing this code
from general framework knowledge will very likely reintroduce them.

## Supported stacks

| Layer | Supported | Templates | Not supported — stop and say so |
|---|---|---|---|
| Backend | NestJS (any version with `@nestjs/swagger` support) | `templates/backend/` | Fastify standalone, Koa, Django/Rails/Go/etc. |
| Backend | Express + **TypeScript** (the "E" in MERN, or a bare Express API) | `templates/backend-express/` | Plain-JS Express (no `tsconfig.json`) — tsoa needs real TS types to read; don't attempt a JSDoc-only fallback without discussing it first |
| Frontend | React SPA — Vite or CRA | `templates/frontend/` | — |
| Frontend | Next.js — App Router or Pages Router | `templates/frontend/` + `templates/frontend-next/` | — |
| Frontend | Vue, Svelte, Angular | — | Not covered by any template here |

Both backend tracks converge on the same `@hey-api/openapi-ts` codegen step
and the same `templates/client-lib/` aggregator — that layer only ever
consumes an `openapi.json`, so it doesn't care which framework produced it.
The two backend tracks diverge only in **how the spec and the auth scaffold
are produced** (Step 1 and Step 3 below). If Step 0 finds a shape not in this
table — stop and say so, don't force the pattern onto it.

**Honest limitation, not a gap to silently paper over:** the auth layer this
skill builds (`AuthenticationManager`, token storage) is browser-session
based — it reads/writes `localStorage` and only makes sense in code that
actually runs in the browser. In a Next.js app that means **Client
Components** (data fetched via `useEffect`, React Query, SWR, etc.). It does
NOT give Server Components, Route Handlers, or Server Actions a way to
authenticate — those run on the server and have no `localStorage` to read.
If the target app needs server-side authenticated fetches in Next, that's a
different, cookie-based pattern and out of scope here; say so explicitly at
G0 rather than implying this migration covers it.

## Non-negotiables

- **One service and one frontend consumer group per increment.** Never
  decorate/type every controller in the backend, or migrate every
  hand-written API type on the frontend, in a single pass. Pick one, finish
  it, verify it, report it, then ask before continuing.
- **Decorating/typing for spec generation is additive only.** Adding
  `@nestjs/swagger` decorators, or shaping a tsoa controller/DTO, must not
  change an endpoint's runtime behavior. If getting a clean spec would
  require a real refactor (e.g. splitting an entity from a response DTO that
  doesn't exist yet), that's its own explicitly-approved step, never folded
  silently into "just adding decorators."
- **Never delete a hand-written API type file until nothing imports it.**
  Grep for it by name after migrating a consumer off it — an empty grep is
  the only acceptable proof, not "I don't think anything else uses it."
- **Never hand-edit a `*.gen.ts` file.** If the generated output is wrong,
  the fix belongs in the source decorators/types; regenerate. A hand-patched
  generated file defeats the drift check that's supposed to catch exactly
  that kind of divergence.
- **Never introduce a second, competing user/auth store.** If the target repo
  already has a User model (a Mongoose/TypeORM/Prisma model, most often) or
  an auth mechanism, adapt the auth templates to use it — don't scaffold a
  parallel in-memory one alongside a real one. This is the single most likely
  way this migration silently breaks something, on any stack.
- **Report every verification with the actual command and actual output.**
  "Typecheck should pass" is not a finding. Run it, paste what it printed.

## Known gotchas (read before writing any code)

These are not theoretical — each one was hit and diagnosed against a real
running backend (or, for the items marked accordingly, reasoned through by
direct analogy while extending the verified NestJS/React path to Express and
Next.js). Skipping past them will cost real debugging time.

### Cross-stack

1. **`@hey-api/openapi-ts` and `@hey-api/client-axios` must be version-matched, not both "latest."**
   The generator emits code against a specific shape of the client's
   `Options`/`Client` types, and that shape has changed across
   `@hey-api/client-axios` releases. Installing the newest `client-axios`
   against an older `openapi-ts` produced real compile errors
   (`Type 'X' does not satisfy the constraint 'TDataShape'`,
   `Property 'client' does not exist on type 'Options<...>'`) in the
   *generated* file, not in anything hand-written. Fix: `npm view
   @hey-api/openapi-ts time --json` and `npm view @hey-api/client-axios time
   --json` to find the `client-axios` version that was current when the
   installed `openapi-ts` version was published, and pin to that exact
   version (not `^`). After installing, run the generate script and confirm
   `tsc --noEmit` on the client lib is clean — a version mismatch here
   surfaces immediately as a compile error in `services.gen.ts`, not as a
   runtime bug, so this is cheap to catch if you check it.

2. **Do not reach for the `axios-auth-refresh` library's `deduplicateRefresh`
   option to handle concurrent 401s — verify this claim yourself before
   trusting it either way, package behavior can change across versions.**
   At the version tested while building this reference (5.0.2, the latest at
   the time), direct reproduction against a real backend showed: with N
   genuinely concurrent 401s on one axios instance, `deduplicateRefresh:
   true` retries only the ONE request that happens to trigger the refresh —
   every other concurrently-failing request is rejected outright, not
   queued, despite the library's own README describing it as "stalling
   additional requests... and resolving them when a new token is available."
   The fix used here is a **hand-rolled** response interceptor
   (`templates/client-lib/single-service/configure.ts`) built directly on
   this SDK's own single-flight `AuthenticationManager.refresh()` — every
   caller shares the same in-flight promise, so N concurrent 401s produce
   exactly one `/auth/refresh` call and every stalled request gets correctly
   retried. This is backend-framework-agnostic (it lives entirely in the
   frontend client-lib). Before using this template, prove the fix still
   holds: register a user, wait past the access-token TTL, fire 3+
   concurrent authenticated requests, and confirm ALL of them succeed with
   exactly one refresh call server-side (add a `console.log` in the refresh
   handler and count lines). If a future version of `axios-auth-refresh`
   fixes this, that's a reason to reconsider — not a reason to skip verifying
   it on this repo.

3. **The axios client's `setConfig()` key is `baseURL`, not `baseUrl`.**
   `@hey-api/client-fetch` (if the target repo currently uses it) uses
   `baseUrl`; `@hey-api/client-axios` uses `baseURL`. This is a silent
   TypeScript-valid mistake if you get it wrong in a spread/object literal
   without a type error pointing at it directly — check the actual generated
   `Config` type (`grep -n "baseURL" node_modules/@hey-api/client-axios/dist/*.d.ts`)
   rather than assuming.

4. **The generated axios client's `result.error` is truthy on ANY failure,
   including a pure network error with no HTTP response at all** — the
   generated code does `error = response?.data ?? {}` in its catch block, so
   a network timeout produces `error: {}`, not `undefined`. When deciding
   whether a failed refresh means "the session is over" vs. "transient
   failure, don't log the user out," check `result.response?.status`
   (400/401/403 → session over; anything else, including `undefined` →
   rethrow, do not force logout). Checking only `if (result.error)` will
   log users out over ordinary network blips.

### NestJS backend

5. **NestJS defaults every `@Post()` to HTTP 201, regardless of what
   `@ApiResponse` documents.** `login` and `refresh` are semantically 200 OK
   (they don't create a resource) — without an explicit `@HttpCode(200)`,
   the actual runtime response is 201 while the generated spec/client says
   200. This is exactly the kind of contract drift this whole approach
   exists to prevent, caught here specifically because a live network trace
   during testing showed `POST /auth/refresh -> 201` instead of the
   documented 200. Verify with a real curl/request after wiring the
   controller, don't assume the decorator matches the runtime status.
   **This is Nest-specific — do not port the `@HttpCode(200)` workaround
   into the tsoa/Express controllers; see gotcha #7.**

### Express + tsoa backend

6. **tsoa has no automatic exception filter — you must wire your own Express
   error-handling middleware, or every thrown error becomes an HTML 500.**
   Nest wraps every route in an exception filter automatically; a thrown
   `UnauthorizedException` always becomes a real 401 JSON body with no extra
   code. Express (and tsoa on top of it) does nothing of the kind — a thrown
   `HttpError`, tsoa's own `ValidateError` on a malformed request body, or
   `expressAuthentication`'s rejection all fall straight through to
   Express's default handler, which returns a `text/html` 500 page, not the
   JSON shape `ErrorResponseDto` and the generated client both expect. Use
   `templates/backend-express/error-handler.ts`, and register it — via
   `app.use(errorHandler)` — **after** `RegisterRoutes(app)`, which must
   itself come after `app.use(express.json())`. Verify with a real curl
   against a route that should 401 or 422 and read the actual response
   `Content-Type` and body, not just the status code.

7. **tsoa's default success status is 200 for every method, unlike Nest's
   POST-defaults-to-201.** Don't carry gotcha #5's `@HttpCode(200)` fix over
   into the Express track out of habit — there's nothing to fix here by
   default. Still verify the actual runtime status with curl per the
   Automated checks below; don't skip the check just because the known Nest
   bug doesn't apply.

8. **tsoa validates request bodies by structural TYPE SHAPE, not by
   business rules.** A DTO field typed `password: string` guarantees "a
   string was sent," not "at least 8 characters," the way Nest's
   `class-validator` `@MinLength(8)` did — there's no bundled equivalent.
   tsoa supports some JSDoc validation tags (`@minLength`, `@maxLength`,
   `@pattern`) on interface fields, but the exact supported tag set has
   changed across tsoa versions — verify against the installed version's
   docs before relying on one rather than assuming parity with the Nest
   track. If a business-rule check actually matters for a given field,
   enforce it explicitly in the service layer.

9. **`expressAuthentication` (tsoa's equivalent of a Nest guard) does not
   automatically attach its result to `req.user`.** tsoa only uses the
   resolved value to decide whether the request is allowed through; making
   the decoded principal available inside the controller method requires the
   function to mutate the real Express `request` object itself as a side
   effect (see `templates/backend-express/auth/authentication.ts`) — this is
   the standard workaround, not an oversight in that template.

### Next.js frontend

10. **`localStorage`/`window` don't exist during server rendering.** Every
    access in `templates/client-lib/*/managers/AuthenticationManager.ts` is
    already guarded with `typeof window !== 'undefined'` for this reason —
    if you hand-write anything that touches these APIs outside that guarded
    module, guard it the same way, or Next will throw
    `ReferenceError: localStorage is not defined` the first time that code
    path is reached during SSR (including the initial server-rendered pass
    of a page that's also client-interactive).

11. **Don't read `AuthenticationManager.isAuthenticated()` in a `useState`
    initializer.** That runs during the very first client render, which
    React requires to match the server-rendered markup exactly — and the
    server always renders the logged-out shape (no `localStorage` to check).
    Reading it inside a `useEffect` instead (see
    `templates/frontend-next/ApiClientProvider.tsx`) defers it until after
    hydration and avoids a hydration-mismatch warning/flash-of-wrong-state.

12. **Only `NEXT_PUBLIC_*`-prefixed env vars reach the browser bundle.**
    `process.env.API_BASE_URL` (no prefix) silently reads as `undefined`
    client-side even though the identical line works in a Server Component
    or Route Handler — this is not a type error, it fails at runtime the
    first time a request goes to `undefined/...`. Use
    `NEXT_PUBLIC_API_BASE_URL` (single-service) or one
    `NEXT_PUBLIC_*_SERVICE_URL` per service (multi-service/EnvironmentManager
    shape). Contrast with Vite (`import.meta.env.VITE_*`) and CRA
    (`process.env.REACT_APP_*`) — confirm which convention actually applies
    by checking the target repo's existing env var usage at G0, don't assume.

13. **`configureApiClient()`/`EnvironmentManager.configure()` needs a client
    component boundary, not a plain top-level call.** There's no single
    `main.tsx` bootstrap file the way a Vite/CRA SPA has. Wire it inside
    `templates/frontend-next/ApiClientProvider.tsx`, marked `'use client'`,
    rendered near the root — `app/layout.tsx` (a Server Component is fine)
    for App Router, `pages/_app.tsx` for Pages Router. Don't try to call it
    directly from a Server Component; it will fail at build/runtime since
    `configureApiClient` touches the axios instance and, transitively, the
    auth manager's browser-only code paths.

## The gates

| | Gate | What it produces |
|---|---|---|
| G0 | Discover | An inventory of the target repo's current state (backend framework, frontend framework, router type if Next) + a proposed single starting increment — **stop for confirmation before touching anything** |
| G1 | Decorate/Type | The exact controller(s)/DTO(s) about to be decorated or typed (or the existing spec to reuse as-is) — **approve before running the spec generator** |
| G2 | Auth design | Single `configureApiClient` vs full `ServiceLoader`/`AuthenticationManager`/`EnvironmentManager`, and — if auth is being introduced or already exists — an explicit statement of how the new SDK's auth coexists with or replaces it, PLUS (Next.js only) confirmation that the scope is client-side data fetching, not Server Components/Route Handlers/Server Actions. **This is never auto-resolved, even when it looks obviously additive.** |
| G3 | Consumer | The one frontend file/resource group being cut over this round, and which hand-written type it currently depends on |
| G4 | Verify | All automated checks below, run for real, with literal output |
| G5 | Retire (optional) | Confirmation the old hand-written type has zero remaining consumers before deleting it |

**Automated checks**, each with a real command and real output — never
asserted, always run:

- Spec contains the expected operationIds/schema names (`grep` the generated
  `openapi.json`, don't just check the file changed)
- Generated client types contain real field names, not a hollow
  `{ [key: string]: unknown }` shape (open `types.gen.ts` and look)
- Backend typechecks: `tsc --noEmit -p <real tsconfig>`, not a cached/Nx
  target (see the sibling gotcha in `templates/demo/check-types.sh`)
- Frontend typechecks, same caveat
- Regenerating a second time produces a zero-diff (`git status --porcelain`
  on the generated output dir is empty) — proves the pipeline is
  idempotent and that "regenerate" was actually invoked, not skipped
- If auth was touched: `templates/demo/demo-refresh-flow.sh` passes all 7
  steps against the real running backend
- If auth was touched and concurrency matters here: fire 3+ concurrent
  authenticated requests right at token expiry and confirm exactly one
  refresh call happened server-side (see gotcha #2 — don't skip this)
- Express track only: a request to a route that should 401/422 actually
  returns a JSON body with that status — not an HTML 500 (gotcha #6)

## Step 1 — Spec generation (Gate G1)

### If the backend is NestJS

If the target controller doesn't have `@nestjs/swagger` decorators yet, add
them — `@ApiTags`, `@ApiOperation({ operationId, summary })` (explicit
`operationId` on every route; without it Nest derives an ugly
`ControllerName_methodName` and the generated client's function names follow
suit), `@ApiResponse` per status code, `@ApiProperty` on every DTO field.
Show the exact diff and get it approved before generating anything — this
touches real production code.

Copy `templates/backend/generate-spec.ts` and `templates/backend/swagger-config.ts`
into the backend, filling in `{{RELATIVE_PATH_TO_CLIENT_LIB}}` and
`{{SERVICE_TITLE}}`. Wire a `spec` script (`ts-node -T src/generate-spec.ts`,
or the equivalent for whatever runs this backend) and run it.

### If the backend is Express + TypeScript

If the target route handler doesn't have a tsoa controller yet, write one —
a class extending `Controller` (from `'tsoa'`) with `@Route`/`@Get`/`@Post`/
`@Body` decorators, and plain TypeScript interfaces for request/response
DTOs (tsoa reads the spec from the TS type shape directly — no runtime
decorator metadata needed on the DTOs themselves, unlike `class-validator`).
See `templates/backend-express/auth/auth.controller.ts` and its sibling
`dto/*.ts` files for the reference shape, and gotcha #8 for what this
approach does and doesn't validate. Show the exact diff and get it approved
before generating anything — this is still real production code, even
though tsoa's DTOs are plainer than Nest's.

Copy `templates/backend-express/tsoa.json` into the backend root, filling in
`{{ENTRY_FILE}}` (the file tsoa's AST parser starts from — typically wherever
`app.listen(...)` is called, or a dedicated `src/index.ts`),
`{{RELATIVE_PATH_TO_CLIENT_LIB}}`, and `{{SERVICE_TITLE}}`. Add a script —
`tsoa spec` (spec only) or `tsoa spec-and-routes` (spec + the Express route
handlers) — and run it. Like the NestJS path, this parses source and writes
`openapi.json` without starting the HTTP server.

**A1**: grep the resulting JSON for the specific operationIds/schema names
just added — not just "the file exists."

## Step 3 — Aggregator + auth layer (Gate G2)

**If this is the first service being migrated in this repo**, decide single-
vs multi-service shape from Step 0's service count:

- **Single backend** → copy everything under `templates/client-lib/single-service/`
  (`configure.ts`, `managers/AuthenticationManager.ts`, `index.ts`).
- **True microservices** → copy everything under `templates/client-lib/multi-service/`
  (`ServiceLoader.ts`, `helpers/EnvironmentManager.ts`,
  `managers/AuthenticationManager.ts`, `index.ts`). This variant is an
  adaptation of the verified single-service pattern — it has not been
  execution-tested end-to-end against a live multi-service refresh flow the
  way the single-service path has. Sanity-check it against the target's real
  second/third service before trusting it blindly.

Fill in every `{{PLACEHOLDER}}` (token storage key, event name, package
names, service names). This client-lib layer is the same regardless of
backend framework or frontend framework — it only talks to the generated
axios client.

**If the target has no auth at all yet**, also copy the auth scaffold that
matches Step 0's backend framework:

- **NestJS** → everything under `templates/backend/auth/` (constants, guard,
  token store, service, controller, module, DTOs), wired into `AppModule`.
- **Express + TypeScript** → everything under `templates/backend-express/auth/`
  (constants, `authentication.ts`, token store, service, controller, DTOs),
  plus `templates/backend-express/http-errors.ts` and
  `templates/backend-express/error-handler.ts` wired per gotcha #6 — this
  is the part most likely to be skipped by habit since Nest doesn't need an
  equivalent, and skipping it breaks every error response, not just auth's.
  Use `templates/backend-express/server-wiring-snippet.ts` as the reference
  for merging `RegisterRoutes(app)` + the error handlers into the target
  repo's real, existing Express entrypoint — there's no single file to copy
  wholesale the way Nest's `AppModule` import is, so this has to be merged
  by hand into whatever file currently calls `app.listen(...)`.

Either way, the `UsersService`/`UserEntity` files are explicitly marked
DEMO-GRADE — if the target already has a real user model (very often a
Mongoose schema in a MERN repo), point `AuthService` at that instead of
copying these two files.

**If the target already has an auth mechanism**, this is the point where G2
requires an explicit, human-approved statement of how the new SDK's
interceptor-based auth coexists with or replaces it. Do not silently layer a
second auth system on top of an existing one.

Wire the frontend bootstrap per Step 0's frontend framework:

- **React (Vite/CRA)** → `configureApiClient()` (or
  `EnvironmentManager.configure()`) once at the app's bootstrap (`main.tsx`
  / `index.tsx`), and a login/register UI backed by `AuthenticationManager`
  if the target has none — see `templates/frontend/LoginForm.tsx` and
  `templates/frontend/App.tsx` for a minimal example (session state + a
  `SESSION_EXPIRED_EVENT` listener that takes over the redirect with
  `preventDefault()` instead of the SDK's default hard
  `window.location.href = '/'`).
- **Next.js** → copy `templates/frontend-next/ApiClientProvider.tsx` and
  `templates/frontend-next/LoginForm.tsx`. Render `<ApiClientProvider>`
  near the root (`app/layout.tsx` for App Router, `pages/_app.tsx` for Pages
  Router) — see gotchas #10–13 before touching this, they cover real
  SSR/hydration/env-var traps that don't exist in the Vite/CRA path. Confirm
  with the user, as part of G2, that the scope is client-side data fetching
  only (per the limitation called out in **Supported stacks**).

## Step 4 — Migrate one frontend consumer (Gate G3)

Rewrite exactly one file's imports from its hand-written API type onto the
generated one, importing through the aggregator package — never straight
from `.../generated`. Do not touch that type's other consumers yet.

In a Next.js app, confirm the file being migrated is a Client Component
(`'use client'` at the top, or a descendant of one) before wiring it to the
aggregator — a Server Component calling into code that touches
`localStorage`/`AuthenticationManager` will fail per gotcha #10.
