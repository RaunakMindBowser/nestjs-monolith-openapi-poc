The Problem

One repo doesn't mean
one source of truth

Being a monolith doesn't remove the tax — it just makes it easy to miss, because the fix (importing something from the backend) is one keystroke away.

📋

Hand-copied DTOs, still

Same repo, same commit — and the frontend still hand-types PatientDTO because nobody wired the backend's actual return type through. It's real: our own admin/patient/@types/index.ts does exactly this.

Proximity isn't the same as a contract.

🩻

"Just import the entity" leaks internals

One `import` away from the ORM model. Every internal-only field — a risk score, an SSN, anything @Exclude()-d at runtime — is sitting right there in the type, waiting for someone to render it.

See Entity vs DTO below — it's provable, not hypothetical.

🕰️

Dates lie about themselves

The backend holds a real Date. JSON only ever sends a string. A hand-copied or entity-imported type says Date; the value that actually arrives is a string. TypeScript won't catch it — it compiles either way.

Wrong at runtime, invisible at compile time.

If you already use @nestjs/swagger, you're most of the way there — you're likely already writing some of the decorators this needs for your Swagger UI page. The only thing usually missing is an explicit operationId per route (see Spec Explorer) and separating your response DTO from your entity/ORM model (see next section) if you haven't already.

The Flagship Argument

"Why not just import the entity?"

Because it's one import away from correct, and the compiler will not stop you. Here's the actual code from this repo.

Internal — never exported

apps/backend/src/patients/patient.entity.ts

export interface PatientEntity {
  id: string;
  mrn: string;
  firstName: string;
  lastName: string;
  dateOfBirth: Date;
  gender: 'MALE' | 'FEMALE' | 'OTHER';
  email: string;
  ssn: string;
  riskScore: number;
  createdAt: Date;
}
The actual contract

apps/backend/src/patients/dto/patient-response.dto.ts

export class PatientResponseDto {
  @ApiProperty() id!: string;
  @ApiProperty() mrn!: string;
  @ApiProperty() firstName!: string;
  @ApiProperty() lastName!: string;
  @ApiProperty({ format: 'date' })
  dateOfBirth!: string;
  @ApiProperty({ enum: ['MALE','FEMALE','OTHER'] })
  gender!: 'MALE' | 'FEMALE' | 'OTHER';
  @ApiProperty() email!: string;
  @ApiProperty({ format: 'date-time' })
  createdAt!: string;
}
Gap 1 — sensitive fields leak

ssn and riskScore exist on PatientEntity. Import that type into the frontend and both are one autocomplete away from a JSX template. Generate from PatientResponseDto instead, and they structurally cannot appear — they were never in the contract.

Gap 2 — dates are wrong twice

The entity's dateOfBirth: Date is real in memory but JSON can only ever send a string. Import the entity type and TypeScript will happily let you call .getMonth() on a value that's actually a string at runtime — no error, no warning, wrong every time.

Verified, not asserted: generating the spec from this repo's decorators and inspecting the output —

The Solution

Code-First OpenAPI Pipeline

Decorators are the input. The spec is a build artifact, not a hand-maintained file. No server needs to be running to produce it.

01 · Decorate

Controllers and DTOs carry @ApiOperation/@ApiProperty — code you'd write for the Swagger page anyway.

02 · Dump

npm run backend:spec boots Nest, builds the document, writes JSON, exits. No port ever opens.

03 · Generate

Same @hey-api/openapi-ts generator as the YAML version — it doesn't know or care where the spec came from.

04 · Stay Safe

Rename a decorated field → both the backend's mapping code and the frontend fail to compile. See Live Demo.

AI Context Win

Same prompt. Radically different results.

Prompt · "Write a function that fetches a patient by ID and returns their record"
✕
Without a generated client

AI guesses the shape from the field name and common conventions:

// AI has to guess everything
interface Patient {
  id: number;         // ❌ wrong — should be string
  name: string;        // ❌ wrong — spec has firstName/lastName
  dob: Date;            // ❌ wrong field name AND wrong type —
                         //    wire format is a string, field is dateOfBirth
  ssn?: string;          // ❌ this field isn't in the API response at all
}

async function fetchPatient(id: number) {
  const res = await fetch(`/api/patients/${id}`); // ❌ wrong URL, no auth
  return res.json() as Patient;
}
dob vs dateOfBirth id is number not string ssn doesn't exist in the API Missing x-api-key header
✓
With @org/api-client

AI reads the generated package — exact shape, auth wired, nothing to leak:

import { getPatient } from '@org/api-client';
import type { PatientsApi } from '@org/api-client';

// AI knows the exact return type from the generated spec
async function fetchPatient(
  id: string,
): Promise<PatientsApi.PatientResponseDto> {
  // getPatient() is generated: URL, x-api-key header, path param handled
  const result = await getPatient({ path: { id } });

  if (result.error) {
    // ErrorResponseDto — typed, not `unknown`
    throw new Error(result.error.message);
  }

  // dateOfBirth: string (ISO) — exactly what the server sends
  // no ssn field exists on this type to accidentally render
  return result.data!;
}
Exact types from the spec Auth header wired automatically dateOfBirth typed as string No ssn field to leak

The generated package is machine-readable context, and it exists whether or not you run microservices. Tell the AI to use @org/api-client and it reads the same types the compiler does — correct by construction, not by luck.
